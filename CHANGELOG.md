- **HIVEMIND room-chat mirror, off by default.** After ChatBridge appends an accepted chat to `inbox.jsonl`, it can hand that chat to the existing Node Appwrite client (`web/muse/messageMirror.js`). The handoff is asynchronous and bounded (a few retries, a queue of 32). A failure is logged as an operation and a status code and does not block delivery. `HIVEMIND_MESSAGE_MIRROR` must be `1` or nothing is written, even when `APPWRITE_*` is set. This does not enable the flag in a deployed environment, rebuild Pages, or change a droplet. `node --test tests/muse/messageMirror.test.js tests/muse/hivemind.test.js` passes. `dotnet test tests/Chief.Bridge.Tests` passes (297). Docs: `docs/hivemind.md`, `docs/chatbridge.md`, `.env.example`.

- **ChatBridge ingress keeps arrival order for a shared recipient.** A fan-out left on `{base}/agents/ingress.jsonl` because the sender inbox lock is busy is no longer passed by a later chat to the same agent. That later line is retained on the journal until the older one is routed, including after a restart, so the shared inbox `seq` stays in arrival order. A line that does not share a recipient is still routed immediately. Test: `Mixed_agent_fanout_and_human_chat_keep_fifo_when_the_sender_lock_is_busy`. `dotnet test tests/Chief.Bridge.Tests` passes (291). Docs: `docs/chatbridge.md`, `knowledge/chatbridge-mention-inboxes.md`.

- **ChatBridge fan-out: keep a sender-lock miss, and refuse an unresolved parent.** An agent fan-out is flushed to `{base}/agents/ingress.jsonl` before the sender inbox is read for parent, root, and hop. If that sender lock stays busy, the line stays in the ingress journal and is routed on a later chat or when the process opens the router again, instead of being dropped with no journal. A `"parent"` or `"root"` that is not in the sender inbox, or a parent whose chain root disagrees with `"root"`, is not delivered and does not start a new root, so unknown-parent replies cannot alternate at hop 1. Draining `deferred.jsonl` flushes the destination inbox to disk before that journal is truncated. Recipient lock timeouts still spill to `deferred.jsonl` and file on the next lock. Fan-out hops stay scoped to one causal root. Torn-tail repair still only appends a missing newline or truncates the partial suffix. `dotnet test tests/Chief.Bridge.Tests` passes (290). Docs: `docs/chatbridge.md`, `knowledge/chatbridge-mention-inboxes.md`.

- **ChatBridge mention inbox: lock-timeout retry, causal fan-out hops, safer torn-tail repair.** A per-agent inbox lock that stays busy past the two-second wait no longer drops the mention. The line is appended to that agent's `deferred.jsonl` and filed into `inbox.jsonl` on the next lock, including after a restart, so `inbox pending` shows it once the lock is free. Fan-out hop state is the deepest hop in the causal chain (`parent` / `root` on the wake), not the highest hop ever stored for that agent, so an old hop-1 delivery does not block `!fanout` for a later human task after ack or restart. The same chain still stops at `max_fanout_hop`. A torn JSONL tail is repaired by appending a missing newline or truncating the partial suffix. The valid prefix is not rewritten. `dotnet test tests/Chief.Bridge.Tests` passes (287). `dotnet test tests/Chief.Knowledge.Tests` passes (33). - **Receive-idle watchdog for a half-dead socket.** hack.chat can leave a WebSocket looking connected after traffic stops. After `onlineSet`, any inbound server frame (chat, info, warn, onlineAdd, onlineRemove, onlineSet, and anything else) refreshes the idle clock. Chat is not required. If nothing arrives for `receive_idle_s` (default **300**; `0` disables; negative, non-finite, or above 86400 is exit 2), the bridge cancels that session, records `receive_idle` (quiet socket), writes `state.json` with `reconnecting: true` and `reason`, and uses the existing backoff. It does not kill the process. The timer is armed only after the join is confirmed and is disarmed for the whole reconnect backoff, so it cannot fire or pile reconnects during a maintenance window. An **external** process watchdog should use a longer clock — **360s** when the internal timeout is 300s — so the bridge rejoins first and the two do not fight. The trip password stays out of the reason, the log, and `state.json`. Docs: README, `agents/chief.md`, `knowledge/receive-idle-watchdog.md`.

- **Reply lock: never restart the bridge under `flock`.** Decide-and-reply takes an exclusive `flock` on `<base>/hook/reply.lock` (or another path under the bridge base that ends in `reply.lock`) so two wakes cannot both send a channel reply. The lock belongs to the open file description. Starting the long-lived bridge while that description is open — `hc restart`, `dotnet Chief.Bridge.dll`, or `chief-bridge` — lets the process inherit the descriptor and hold WRITE until it exits. Later `flock` calls then block. `status` can still show the pid running and connected. Production recovered when the bridge was restarted from a shell that was not inside `flock`. Operators take the lock with `flock -w N` (a short timeout; exit 1 means busy), and on a busy lock they check `inbox.jsonl` for an agent reply already logged after the inbound chats (`"dir":"out"`, `msg.cmd` of `chat`, no `"auto":"ack"`) instead of sending without the lock. If the bridge pid has that descriptor open, stop it with SIGTERM from an unlocked shell and start it again there. A local restart wrapper closes inherited fds whose path ends in `reply.lock` or `hook/reply.lock` before it spawns the bridge. This repo does not ship `hc` (the Python `bin/hc` was removed with the legacy bridge); the close loop is in the README and `agents/chief.md` for that local wrapper. `reply.lock` is gitignored. Docs: README ("Reply lock"), `agents/chief.md`, and `knowledge/reply-lock-deadlock.md`. No bridge behavior change.

- **Reconnect forever** (#15, merged 2026-09-27 08:39). On 2026-09-27 around 04:40 ET hack.chat dropped the connection. A bridge that had already joined on main came back by itself; another copy of the bridge exited and had to be restarted by hand. There is no 3-attempt counter in `RunForeverAsync`. The give-up at 3 is Muse's first-join cap, and two holes in the bridge could still end a retry:
